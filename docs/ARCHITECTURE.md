# Архитектура

## Основание описания

Состояние на **2026-09-12** зафиксировано по обсуждению проекта, показанным фрагментам кода и результатам ручных проверок на VPS. Полный актуальный `app.py` ещё не перенесён в репозиторий; названия переменных окружения и деталей развёртывания нужно сверить после переноса.

## Компоненты

| Компонент | Роль |
| --- | --- |
| VPS, `/opt/daily-digest` | Постоянно работающая установка |
| Docker, Python | Изолированное выполнение приложения; в показанном Dockerfile используется Python 3.12 и пользователь UID 10001 |
| `app.py` | Команды, парсер, выпуск, очистка, обработка кнопок и планировщик |
| `requests` + BeautifulSoup | Чтение и разбор публичного HTML `t.me/s/<username>` |
| `python-telegram-bot` | Bot API, получение обновлений через polling и JobQueue |
| SQLite | Источники и служебный учёт сообщений |
| `.env` | Локальная конфигурация и токен; передаётся контейнеру при запуске |

`api_id`, `api_hash`, MTProto-сессия и вход в Telegram-аккаунт для этой схемы не требуются. Закрытые каналы не поддерживаются.

## Плановый выпуск

1. JobQueue запускает задачу каждый день в **20:30 `Europe/Moscow`**, с явно заданной зоной времени.
2. Перед сбором удаляются отслеживаемые сообщения чата владельца, включая команды и ответы вне выпуска.
3. Для запуска рассчитывается граница `now - 24 часа`; это скользящее окно, а не календарный день или интервал от последнего успешного выпуска.
4. Активные каналы читаются последовательно. В показанном коде порядок — `added_at`, затем `username`.
5. Парсер извлекает ID, время, текст и ссылку публикации, проходит к более старым страницам через `before`, убирает повторения по ID и отбирает посты по времени.
6. Для каждого канала отправляются заголовок, посты и завершение блока с кнопкой «🚫 Отписаться» (`unsub:<username>`).
7. ID новых сообщений записываются для следующей очистки.

Ошибка чтения одного источника сопровождается предупреждением и не должна препятствовать обработке остальных. Ограниченные повторы отправки снижают влияние временных сетевых сбоев, но не гарантируют полную доставку.

## Ручной выпуск и управление источниками

`/digest` запускает сбор без полной очистки. Несколько ручных выпусков могут временно находиться в чате одновременно; следующий плановый запуск удаляет накопившиеся отслеживаемые сообщения.

Команда удаления и inline-кнопка изменяют `channels.enabled` на `0`. Повторное добавление включает источник снова. Бот ограничивает команды и callback владельцем; отключение источника не меняет подписку владельца в Telegram.

## Хранение и очистка

Локальная база — `/opt/daily-digest/data/digest.sqlite3`. При показанном запуске каталог монтируется как `/data`, а `DATA_DIR=/data` передаётся через окружение.

| Таблица | Данные |
| --- | --- |
| `channels` | `username`, `enabled`, `added_at` |
| `digest_messages` | ID сообщений выпуска: `chat_id`, `message_id` |
| `chat_messages` | Все отслеживаемые ID сообщений чата владельца: `chat_id`, `message_id` |

При доработке очистки известные ID из `digest_messages` мигрировали в `chat_messages`. Входящие сообщения владельца учитываются отдельным обработчиком; исходящие — через обёртки отправки и ответов. Очистка идёт от новых ID к старым. Успешно удалённые и окончательно недоступные ID исключаются из учёта; после временных сетевых ошибок ID сохраняются для следующей попытки. Список источников не очищается.

«Без истории» означает отсутствие архива публикаций и команд его просмотра. Служебные ID и настройки сохраняются между перезапусками; база целиком не обнуляется.

Бот не получает произвольную старую историю личного чата через Bot API. Неизвестные ему сообщения, сообщения старше 48 часов и некоторые специальные сообщения могут остаться; ограничения описаны в [deleteMessage](https://core.telegram.org/bots/api#deletemessage). Нулевая длина списка ID сама по себе не доказывает, что весь чат пуст: нужна проверка в Telegram.

## Сетевые ошибки

По показанной доработке:

- Отправка сообщений выпуска: **до 4 попыток всего**, с увеличивающейся задержкой при `TimedOut` / `NetworkError`. После исчерпания попыток ошибка записывается в журнал, обёртка возвращает `None`, обработка выпуска продолжается.
- Очистка: **до 3 попыток на ID** при тех же временных сетевых ошибках. `BadRequest` считается окончательной ошибкой для данного ID.
- Таймауты клиента Bot API: `connect=30`, `read=60`, `write=60`, `pool=30` секунд. Это показанные настройки ApplicationBuilder, а не гарантия таких таймаутов для каждого отдельного HTTP-запроса или polling.

Если Telegram принял сообщение, но ответ потерялся по таймауту, повторная отправка может дать дубликат. Отправки и SQLite не образуют общую транзакцию; после аварии возможны неучтённые сообщения.

## Ограничения

- Веб-просмотр Telegram может быть недоступен или изменить HTML. Это не официальный API истории каналов.
- В показанном парсере предел обхода — **12 страниц на канал**, HTTP-таймаут чтения страницы — **20 секунд**. Очень активный канал может не поместиться в этот предел.
- Длинный текст сокращается примерно до 3000 символов при форматировании; есть ссылка «Открыть пост». Полное воспроизведение медиа не гарантируется.
- Очистка выполняется до отправки нового выпуска: при сбое после очистки чат может остаться пустым или с частичным выпуском.
- Запуск в 20:30 означает начало задачи; доставка большого выпуска занимает время.
- Автоматическое восстановление пропущенных дней не подтверждено. Скользящее окно не восполняет публикации старше 24 часов после простоя.
- Должен работать один экземпляр бота: несколько процессов могут конфликтовать при polling, отправках и очистке.
